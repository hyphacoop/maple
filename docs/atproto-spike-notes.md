# ATProto spike — running notes

Working notes for the spike (epic #58). Each issue appends its "Problems discovered" here; the findings write-up (#67, `docs/atproto-spike-findings.md`) consolidates them.

## #59 Local ATProto dev environment

**What landed:** `yarn atp:dev` boots `TestNetworkNoAppView` (in-process PLC :2582 + PDS :2583, SQLite, no AppView) via `scripts/atproto/dev-env.ts`. Deps: `@atproto/api@^0.19.19` (dependency), `@atproto/dev-env@0.4.9` (devDependency, exact pin) plus yarn `resolutions` pins. README section under "Developing Locally".

**Problems discovered:**

1. **ESM/node-22 wall.** All `@atproto/*` packages published since 2026-05-18 (`dev-env` ≥0.5.0, `api` ≥0.20.0) are ESM-only with `engines.node >=22`. MAPLE is node ^20 + yarn 1 classic (hard engine enforcement) + CJS script toolchain, so the spike pins the last CJS train: `dev-env@0.4.9` (exact) + `api@^0.19.19`. **Production adoption would require migrating MAPLE to node ≥22 and tolerating ESM-only deps** (Next 14 handles ESM deps, but the ts-node/CJS script toolchain would not).
2. **Caret drift across the ESM boundary.** Bluesky kept publishing node-22-only releases _within the same semver lines_ dev-env 0.4.9 depends on via carets (e.g. `@atproto/ozone ^0.1.174` resolved to 0.1.176, which requires node ≥22 → `yarn install` fails engine checks). Fixed with `resolutions`: `@atproto/bsky 0.0.230`, `@atproto/bsync 0.0.25`, `@atproto/ozone 0.1.174`, `@atproto/pds 0.4.223`. Fragile: the pinned train receives no fixes.
3. **Server-package `.d.ts` files don't parse under TypeScript 5.3.3.** `@atproto/pds` type declarations (pulled in by `@atproto/dev-env`) use newer TS syntax; `skipLibCheck` does not suppress _syntax_ errors, so `yarn check-types` broke. Fixed by excluding `scripts/atproto` from the root tsconfig (`ts-node --swc` is transpile-only, so the script still runs). **`@atproto/api` itself parses fine under TS 5.3.3** — verified with a standalone `tsc --noEmit` probe — so frontend work in later issues is unaffected.
4. **dev-env works fine outside jest.** `TestNetworkNoAppView.create()` needs no jest globals, no postgres/redis, no env vars; PLC DB is an in-memory mock and the PDS uses SQLite + blob storage under the OS temp dir (not cleaned on exit, left to OS temp cleanup). Confirmed no relay is needed — the single PDS serves its own firehose. The fallback (`TestPds` + `TestPlc` directly) was not needed.
5. Minor: local default node was 24; repo engines `^20` reject it — `nvm use` (`.nvmrc` = 20) before `yarn install` / `yarn atp:dev`.

**Verified AC:** `yarn atp:dev` prints the PDS URL; `curl :2583/xrpc/com.atproto.server.describeServer` → JSON (`availableUserDomains: [".test", ".example"]`, no invite code); `createAccount` for `alice.test` returned a `did:plc:...` + JWTs; Ctrl+C shuts down cleanly and releases ports. Pre-existing unrelated failure: `yarn check-types` errors on stale gitignored `functions/lib/email/helpers.ts` build output (present before this change).

## #60 Lexicon schemas + TS types

**What landed:** `lexicons/org/mapletestimony/{bill,testimony}.json`, hand-written record interfaces and app-type mappers in `components/atproto/{lexicons,mappers}.ts`, and `yarn atp:validate` (`scripts/atproto/validate-lexicons.ts`) which loads all lexicon docs into an `@atproto/lexicon` `Lexicons` container (throws on invalid schema; `com.atproto.repo.strongRef` comes from `@atproto/api`'s exported `schemas`, so nothing foreign is vendored under `lexicons/`), validates sample records built by the real mappers (shared deterministic fixtures in `scripts/atproto/fixtures.ts`), and asserts record→app-type→record round-trips are stable. A jest test (`components/atproto/lexicons.test.ts`) pins the lexicon's `content.maxGraphemes` to the app's `maxTestimonyLength` so the two can't drift silently — note the semantics still differ (graphemes/inclusive vs UTF-16 units/exclusive at the boundary). `@atproto/lexicon@0.6.2` added as an exact-pin devDependency (same pinned-CJS-train policy as #59). `components/atproto/` is inside the root tsconfig, so `yarn check-types` proves the mappers typecheck against the real `Bill` (`components/db/bills.ts`) and `Testimony` (`components/db/testimony/types.ts`) types.

**Schema decisions (dropped/transformed fields):**

_`org.mapletestimony.bill`_ — rkey `${court}-${billId}` (e.g. `193-H1234`; fits the rkey charset `[A-Za-z0-9._:~-]`).

- **Dropped: `testimonyCount`, `endorseCount`, `opposeCount`, `neutralCount`, `latestTestimonyAt`, `latestTestimonyId`.** These are aggregates over _other users'_ records — in ATProto they can only be computed by an AppView consuming the firehose, never stored in a repo record. Mapper fills 0/undefined. This is the single biggest architectural shift: MAPLE's Firestore-transaction counter updates have no repo-side equivalent.
- **Dropped: `content.DocumentText`.** Bill full text can be hundreds of KB; records live in a Merkle repo and should stay small. Would be a blob (`upload_blob` + a `bytes`/blob ref) or fetched from the legislature API on demand. `cosponsorCount` is derivable (`cosponsors.length`) and also dropped.
- **Transformed:** Firestore `Timestamp` fields (`fetchedAt`, `nextHearingAt`) become lexicon `format: datetime` ISO strings (`Timestamp.toDate().toISOString()` / `Timestamp.fromDate(new Date(iso))` shims in `mappers.ts`). Field names camelCased (`Title` → `title`, `MemberReference.Type` → `memberType`, etc.).
- **Gotcha — upstream date strings are not ATProto datetimes.** `BillHistoryAction.Date` values from the MA legislature API (e.g. `2026-02-16T11:17:15.563`) lack timezone offsets, which ATProto's strict `format: datetime` validation rejects. `#historyAction.date` is a plain string preserved verbatim. Any production lexicon needs an explicit policy for upstream-sourced timestamps (normalize to UTC on ingest, or don't claim the datetime format).
- Nullable→optional: runtypes `Nullable`/`Maybe`/`NullStr` fields (history `Date`, committee `email`) map to _optional_ lexicon fields (lexicon has no `null`); mappers restore `null` on the way back in.

_`org.mapletestimony.testimony`_ — rkey `${court}-${billId}` in the _user's_ repo → at most one testimony per bill per user by construction (MAPLE's one-testimony-per-bill rule becomes a free invariant); `putRecord` with the same rkey is an edit.

- **Dropped: all author snapshot fields** (`authorUid`, `authorDisplayName`, `authorRole`, `fullName`, `billTitle`, `representativeId`/`senatorId`/districts). Identity _is_ the repo DID; handle/display-name/role/billTitle are resolved by the caller or an AppView. Mapper takes a `{did, handle, rkey, billTitle?}` context and defaults `authorRole` to `"user"` — role verification (legislators, orgs) would need a labeler or an app-controlled verification record, noted as an open problem for #67.
- **Dropped: `version`, `editReason`.** The PDS stores only the latest record — no version history. MAPLE's edit-history/`editReason` audit trail would have to live in an AppView that archives firehose events. Mapper reports `version: 1` always.
- **Dropped: `attachmentId`/`draftAttachmentId`** (would be repo blobs; out of spike scope), **`public`** (repo records are public by definition — MAPLE's private-draft flow has no repo-side equivalent; drafts would stay app-local), **`ballotQuestionId`** (out of scope).
- **Kept redundantly:** `bill` strongRef _plus_ denormalized `court`/`billId`, so consumers can filter without resolving the ref. StrongRef `cid` pins the bill version the author saw — a small win over Firestore (testimony provably references a specific bill snapshot).
- `content` capped at `maxGraphemes: 10000`, matching `maxTestimonyLength` in `components/db/testimony/types.ts`.

**Problems discovered:**

1. **Counters/aggregates don't exist in repo-land** (see above) — everything MAPLE renders that spans users (testimony counts, latest testimony, "N endorsements") requires an AppView. This reframes #65/#66 from stretch to essential-for-parity.
2. **Upstream timestamp strings violate ATProto `datetime` format** (no timezone offset) — see `#historyAction.date` above.
3. **Skipping lex-cli codegen was right for the spike.** `@atproto/lex-cli` on the current train is ESM-only/node≥22 (same wall as #59); the two hand-written interfaces took minutes. A production adoption with many lexicons would want codegen and thus the node≥22 migration.
4. **PDS accepts unknown-lexicon records with _default_ validation.** Live probe (`scripts/atproto/probe-putrecord.ts`, one-shot: boots `TestNetworkNoAppView`, creates account, `putRecord`s a testimony via `AtpAgent`): `putRecord` succeeded with default validation — do not pass `validate: false`, which would also disable the structural checks, and `getRecord` returned the record byte-identical (rkey `193-H1234` accepted). The PDS does data-model (structural) validation only for NSIDs it doesn't know — schema enforcement for `org.mapletestimony.*` is entirely client-side (`yarn atp:validate` covers CI) unless/until an AppView validates on ingest. Note for #64: nothing stops a hostile client writing garbage into our collections.
5. Minor: `@atproto/dev-env`'s `network.pds.getClient()` returns a lex-client `Client`, not an `AtpAgent` — use `new AtpAgent({ service: network.pds.url })` from `@atproto/api` (which is what the frontend will do anyway).

**Verified AC:** `yarn atp:validate` → 3 lexicon docs load + both sample records valid + round-trips stable; `yarn check-types` → only the pre-existing stale `functions/lib` errors (mappers compile against real app types); live putRecord/getRecord probe green.

## #61 Seed script

**What landed:** `yarn atp:seed` (`scripts/atproto/seed.ts`) seeds the running `yarn atp:dev` network: upserts `maple.test` / `alice.test` / `bob.test` (password `<name>-pass`; login-or-createAccount, so re-runs and network restarts both work), `putRecord`s four real 194th-court bills (`scripts/atproto/seed-data.ts`: H72, S25, H1234, H2246 — snapshots pasted from the malegislature.gov API, no live fetching) into the maple repo via `billToRecord`, writes one bob testimony on H1234 into **bob's** repo with a real strongRef (uri + cid captured from the bill's putRecord response), verifies via `listRecords`, and prints the `NEXT_PUBLIC_ATP_PDS_URL` / `NEXT_PUBLIC_MAPLE_DID` block for `.env.local`. Deterministic rkeys (`recordRkey`) make re-runs pure upserts — verified: second run logs in instead of creating and completes with the same URIs, no errors. The record-size probe lives in `scripts/atproto/probe-record-size.ts` (one-shot, same convention as probe-putrecord.ts; not part of any yarn script). Ports for the dev network are shared via `scripts/atproto/ports.ts` (dev-env.ts boots at import time, so constants can't live there). `testimonyToRecord` now takes only the record-carried fields (`Pick<Testimony, ...>`) so callers — the seed, and later #64's submission flow — pass what they have instead of fabricating a full `Testimony`; full objects still typecheck structurally.

**Problems discovered:**

1. **The authoritative identity is an out-of-band trust anchor.** Nothing in the protocol marks `maple.test`'s repo as "the" bill source — any repo can hold `org.mapletestimony.bill` records, so the app must pin the authoritative DID via config (`NEXT_PUBLIC_MAPLE_DID`, printed by the seed). The DID also changes every `atp:dev` restart (throwaway PLC), so `.env.local` must be refreshed after each reboot — a real dev-loop annoyance. Production would resolve a well-known handle (e.g. `bills.mapletestimony.org` → DID via DNS/`.well-known`) once and pin the result; handle→DID resolution is the trust root either way.
2. **PDS record-size ceiling: 150 KiB.** `putRecord` accepts a JSON body up to exactly 153,600 bytes (150 KiB) and returns HTTP 413 `request entity too large` above (bisected via raw XRPC; it's the xrpc-server `jsonLimit`, a transport-level check — not a repo or lexicon error). Real bill records with summaries fit easily (~2-6 KB), but anything `DocumentText`-sized (hundreds of KB) is impossible as a record, confirming #60's decision to drop bill text (blob or fetch-on-demand). Note the limit applies to the request envelope, so effective record budget is slightly under 150 KiB.
3. **createAccount is not idempotent, createSession is the upsert primitive.** There's no "get or create account" XRPC; the seed's login-first-then-create pattern is the way to make seeding re-runnable. Also note `AtpAgent.login` throws on a _missing_ account and on a _wrong password_ identically (`AuthenticationRequired`), so a password change in the seed constants surfaces as a confusing handle-taken error from the createAccount fallback.
4. **Latent type mismatch in #60's hand-written record types.** `putRecord` takes `record: { [x: string]: unknown }`; TypeScript only grants implicit index signatures to type _aliases_, not interfaces, so `MapleBillRecord`/`MapleTestimonyRecord` as `interface`s didn't typecheck against the agent API (invisible until now because `scripts/atproto` is outside the root tsconfig — surfaced by a standalone `tsc --noEmit` probe of `seed.ts`). Fixed by switching the two record types to `type` aliases in `components/atproto/lexicons.ts`. Lesson for a codegen future: lex-cli generates type aliases for this reason.

**Verified AC:** `yarn atp:seed` after `yarn atp:dev` → 3 accounts, 4 bill records, 1 testimony; re-run → clean (logins + upserts, same URIs); raw `listRecords` on the maple repo returns all 4 bills and on bob's repo the testimony with the real-cid strongRef; `yarn atp:validate`, `npx jest components/atproto`, standalone `tsc` probe of `seed.ts`, and `yarn check-types` (only pre-existing stale `functions/lib` errors) all green.

## #62 ATProto auth provider + /atp/login

**What landed:** `components/atproto/auth.tsx` — a `createService`-based React context (the repo's provider idiom, mounted in `components/providers.tsx` alongside Firebase/Auth/Profile/Search/LogRocket) wrapping a single `AtpAgent` against `NEXT_PUBLIC_ATP_PDS_URL` (default `http://localhost:2583`). Deliberately **not** Redux: the Firebase auth slice is untouched; ATProto session state lives in the context plus one localStorage key (`maple.atproto.session`, helpers in `components/atproto/session-storage.ts`, jest-covered). `login()` wraps `com.atproto.server.createSession` via `agent.login`; the agent's `persistSession` callback is the single writer of both localStorage and React state (`create`/`update` persist, `expired`/`create-failed` clear, `network-error` keeps storage so the next load retries). On mount the provider `resumeSession`s from storage. `logout()` best-efforts `deleteSession` and clears unconditionally. `pages/atp/login.tsx` is a minimal react-hook-form page (shared `Input`/`PasswordInput`/`LoadingButton`, strings in the `auth` i18n namespace) that shows handle + DID and a sign-out button when signed in. `NEXT_PUBLIC_ATP_PDS_URL`/`NEXT_PUBLIC_MAPLE_DID` added to `.env.example`.

**Problems discovered:**

1. **`persistSession` is the whole session-lifecycle API — and `AtpAgent` is already deprecated.** The constructor callback receives `create | update | expired | create-failed | network-error` and is the only hook for persistence; there is no event for "refresh succeeded" distinct from `update`, and `resumeSession` resolves/rejects _after_ firing it, so state management belongs in the callback, not in call sites. The typings mark `AtpAgent` "will be deprecated in the near future — use `Agent` + `CredentialSession`"; the spike stays on `AtpAgent` (same underlying `CredentialSession`) because the older 0.19 CJS train is pinned anyway (#59), but a production adoption starts from `CredentialSession` or OAuth directly.
2. **`network-error` vs `expired` matters for UX.** A refresh that fails because the PDS is unreachable (`network-error`) must not delete the stored session, or a flaky network signs users out permanently; only `expired`/`create-failed` warrant clearing. Verified the inverse path live: a stale/garbage stored session (e.g. any session surviving an `atp:dev` restart — new PLC, old JWTs) fails `resumeSession` with an auth error and is cleared, landing signed-out cleanly. Every PDS restart invalidates browser sessions, same dev-loop annoyance as the `NEXT_PUBLIC_MAPLE_DID` churn from #61.
3. **Dual-auth coexistence is clean at the provider level.** Both providers mount in the same `ServiceProvider` array; Firebase (Redux slice + IndexedDB persistence) and ATProto (context + localStorage) share no state, and the app renders with both active, no console errors. Not exercised end-to-end: a simultaneous Firebase _sign-in_ (needs the emulator suite or the shared dev backend; this session ran frontend-only). The real coexistence question for #64+ is UX, not tech: two independent logged-in/out states with no linkage between a Firebase uid and a DID.
4. **Error opacity confirmed in the UI** (#61 noted it server-side): wrong password and unknown handle produce the identical `AuthenticationRequired` failure, so the form can only say "check your handle and password". Fine for a spike; a production flow wants handle-resolution feedback _before_ the password prompt (resolve handle → DID first, which OAuth's identifier-first flow does naturally).
5. **Why OAuth is deferred.** ATProto's production auth is OAuth (`@atproto/oauth-client-browser`): per-client registration metadata served over HTTPS, PAR + DPoP, PKCE, and a redirect flow — none of which the throwaway localhost dev-env exercises meaningfully, and the pinned pre-ESM train predates the browser client anyway. `createSession` with the account password is the legacy/app-password path: fine against a local PDS you own, unacceptable against real user PDSes (full-credential custody, no scopes, no revocation UI). Findings for #67: the production path is OAuth or nothing; budget for client metadata hosting and the node≥22/ESM migration as prerequisites.

**Verified AC (live, via browser):** `/atp/login` renders with MAPLE chrome; `alice.test`/`alice-pass` → handle + DID render; reload keeps the session (localStorage key present, `resumeSession` green); Sign Out clears storage and survives reload signed-out; wrong password → generic alert; stale-session reload → auto-clear + signed-out form; homepage renders with both auth providers mounted, zero console errors. Battery: `npx jest components/atproto` (2 suites/6 tests), `yarn check-types` (only pre-existing stale `functions/lib` errors), eslint + prettier clean on all new files.

## #63 Bill list + detail pages from ATProto records

**What landed:** `pages/atp/bills/index.tsx` (SSR `listRecords` on the maple repo → MapleCard list: bill number, title, link per row) and `pages/atp/bills/[court]/[billId].tsx` (SSR `getRecord` by deterministic rkey → `billFromRecord` → `AtpBillDetails`), plus `components/atproto/api.ts` (server-side fetch helpers: `mapleDid` — the first consumer of `NEXT_PUBLIC_MAPLE_DID` — `getAtpBill`, `listAtpBills`; missing record/repo → null, transport errors rethrow) and `components/atproto/AtpBillDetails.tsx` (recomposes `BillDetails`'s presentation-only children: BillNumber, Status, Summary, Sponsors, Committees, Hearing — no auth/flags/testimony/follow/tracker). `components/atproto/AtpSetupAlert.tsx` renders setup instructions when the DID env var is unset or the configured repo is missing, instead of misreporting a config problem as a 404. New `atp*` strings in the `auth` namespace. Detail pages follow the Firestore bill page's gSSP pattern (zod query parse → notFound, `JSON.parse(JSON.stringify(bill))` serialization, inline `serverSideTranslations`).

**Component inventory (the probe):** Reusable as-is from props — `BillNumber`, `Status` (provides its own `CourtContext`; `HistoryTable` standalone would need one), `Committees`, `Hearing` (`SponsorsAndCommittees.tsx`), `TestimonyCounts` (reads counters off the bill prop), `SmartDisclaimer`, `SmartIcon`, `Card`/`ListItem`, `links.tsx` helpers, `formatBillId`. _Conditionally_ coupled — `Summary` (its hearing-video branch renders a modal whose private `Hearing({hearingId})` child does Firestore `getDoc`s; note the name collision with the pure `Hearing`) and `Sponsors` (renders Firestore-per-row `Cosponsors` when a bill has >2 non-primary cosponsors). Hard-coupled, must be replaced for ATProto parity — `BillDetails` itself (`useAuth`, `useFlags`), `Cosponsors`, `BillTestimonies`, `TestimonyFormPanel`, `FollowBillButton`, `BillTrackerConnectedView`, and the list side (`BillSearch`/`BillHit` need the Typesense/InstantSearch context; there was no props-only "bill row" component to reuse).

**Problems discovered:**

1. **"Presentational" components embed data fetching levels deep — and gate it on truthiness.** `Summary` enables its Firestore-backed hearing UI on `{hearingIds ? ...}`, so passing `hearingIds: []` would _enable_ it; the safe display shape is `undefined` (`AtpBillDetails` strips the field). Reusing the pure subtree required auditing every descendant, not just the component's own imports.
2. **Sponsors' hidden Firestore path is data-dependent.** The coupled `Cosponsors` modal only renders when a bill has >2 non-primary cosponsors — invisible with the seed bills (≤1), fires on many real bills. A reusability assessment made only against seed data would have missed it (it degrades gracefully: fetches fire on modal open, rows fall back to plain names).
3. **DID config churn bites twice per PDS restart:** `.env.local` must be re-pointed at the new DID _and_ the Next dev server restarted, because `NEXT_PUBLIC_*` vars are inlined at boot. The setup-alert path (rather than 404) exists specifically because this failure mode is routine in the dev loop.
4. **Record reads are untyped and unvalidated.** `getRecord`/`listRecords` return `unknown` values cast to `MapleBillRecord` on trust; per #60 the PDS doesn't enforce our lexicon, so a malformed record in the repo would crash SSR. Production reads should validate with `@atproto/lexicon` before mapping. Missing-record and missing-repo both surface as XRPC 400/InvalidRequest — distinguishing "bad DID" from "no such bill" on the detail page needs the error string, not the status.
5. **Counters render 0 on a real page now** — the parity gap from #60 is user-visible (`TestimonyCounts` shows 0/0/0/0). Reinforces #65/#66: cross-user aggregates need an AppView.
6. **Firestore `Timestamp` leaks through the boundary both ways:** the mapper builds real `Timestamp` instances only for gSSP to flatten them back to `{seconds, nanoseconds}` JSON; it works because consumers (`dateInFuture`/`parseTimestamp`) tolerate the flattened shape, but the app's date plumbing is Firebase-shaped all the way down.
7. **Navigation leaks back into Firebase-land immediately:** `Summary`'s topic SmartTags link to the Typesense-backed `/bills?...` search and `Status`'s history modal links committee/bill references to Firestore-backed pages — a hybrid deployment can't cleanly fence the two worlds.
8. Minor: list pagination cursor unhandled (fine at 4 records); pre-existing latent gap where `Summary`'s `HearingsModal` uses an `editProfile`-namespace key no bill page loads; the app SSRs an empty `__next` shell (all rendering is client-side after hydration — pre-existing, applies to every page), so gSSP "SSR" here means server data fetching, not server HTML.

**Verified AC (live, via browser):** `/atp/bills` renders the 4 seeded bills (H.1234, H.2246, H.72, S.25) in a MapleCard list with working links; `/atp/bills/194/H1234` renders BillNumber, Status (history modal shows all 4 actions), Summary (title, Download PDF link, Smart Summary, topic tag, 0-count TestimonyCounts), Sponsors (lead sponsor with photo), Committee card, full MAPLE chrome — identical signed in (alice.test via `/atp/login`) and signed out, zero console errors. Negative paths: `/atp/bills/194/H9999` and `/atp/bills/abc/H1` → 404; blank `NEXT_PUBLIC_MAPLE_DID` → both pages 200 with null props → setup alert. Battery: `yarn check-types` (only pre-existing `functions/lib` errors), eslint `--max-warnings 0` + prettier clean on all new files, `npx jest components/atproto` green.

## #64 Testimony submission to the user's own PDS

**What landed:** `components/atproto/api.ts` gains `getAtpBillRef` (fresh `{uri, cid}` strongRef for a bill, fetched at submit time so testimony pins the bill version currently in the repo), `getAtpTestimony` (unauthenticated read of any repo's testimony for a bill by deterministic rkey — reusable by #65), and `putAtpTestimony` (authed write composing strongRef fetch → `testimonyToRecord` → `putRecord` into the _signed-in user's own_ repo, rkey `${court}-${billId}`, **default** validation — the issue text said `validate: false`, deliberately not done per #60's probe: default gives structural checks, `false` would disable even those). `components/atproto/AtpTestimonyPanel.tsx` is the minimal panel (position ToggleButtons + shared `TextArea` + LoadingButton; plain `useState`, not the `components/publish/*` redux step machine): sign-in CTA when signed out, prefills from the user's repo, success Alert shows createdAt + uri + cid, button label flips Publish→Update, and `createdAt` is preserved across edits so an overwrite is observable as _uri stable, cid changed, createdAt fixed_. Mounted in `AtpBillDetails` in an md=4 column (md=8 reserved for #65's cross-user list). New `atpTestimony*` strings in the `auth` namespace.

**Problems discovered:**

1. **Stale sessions can resume as "signed in" with a dead identity — #62's cleanup only covers the 401 path.** The dev-env PDS signs JWTs with a fixed secret, so an access token from a _previous_ `atp:dev` instance passes signature verification on a new instance; `getSession` then fails with 400 `Could not find user info for account: <old did>`, not 401. `CredentialSession.resumeSession` treats only 401 as expired — any other failure keeps the session — so the auth provider lands `signedIn` on a DID that no longer exists. Observed live: the panel then showed its load-error alert while the navbar looked signed in. Cleared by removing the localStorage key. A production classifier must treat account-not-found (and DID-resolution failure) as terminal, not transient.
2. **"Missing repo" is not always XRPC 400.** `getRecord` on the dead DID returned **502 UpstreamFailure** (the fresh in-memory PLC can't resolve the old DID), which `api.ts`'s `isMissing` (400 ⇒ null) correctly refuses to swallow — but that also means #63's SSR bill pages would 500 rather than render the setup alert in the same stale-session/stale-DID states. Error taxonomy for reads needs three buckets (missing record / unresolvable repo / transport), not two.
3. **Rkey-upsert destroys history; edit-time is unrepresentable.** The record carries only `createdAt`. The panel preserves it across edits (else every edit looks like a new submission), so there is no updatedAt at all — representing both would need an extra field (self-attested, unverifiable) or an AppView archiving firehose events. MAPLE's 5-edit cap, `editReason` requirement, and per-version archive (`archivedTestimony`) have no repo-side equivalent; the publish-transaction invariants become client-side honor system until an AppView enforces on ingest.
4. **Default-validation behavior confirmed on the real UI path:** `putRecord` responses carry `validationStatus: "unknown"` for `org.mapletestimony.*` — structural checks only, schema enforcement stays client-side (#60's probe finding, now observed end-to-end from the browser).
5. **What porting the real publish flow would demand:** the Firestore flow's seam is `useEditTestimony`'s interface (`draft`/`publication`/`saveDraft`/`publishTestimony`), bound in `usePublishService` — an ATProto twin could swap in there, but only the _publish_ leg maps. Private drafts + debounced autosave are impossible as repo records (records are public by definition; drafts must stay app-local), attachments are blobs (`uploadBlob` + blob refs), and notifications, per-bill counters, and `latestTestimony*` are AppView aggregates. The panel-status state machine (`noTestimony`/`createInProgress`/`published`/`editInProgress`) presumes a draft store that has no repo-side home.
6. **Dual-auth UX is now user-visible:** the bill page renders the Firebase "Log in / Sign up" navbar while the panel manages its own PDS session — two unlinked signed-in states on one page, with no linkage between a Firebase uid and a DID. Fine for a spike, incoherent for a product.
7. Minor: react-bootstrap `ToggleButton` renders a visually-hidden radio input; programmatic clicks on the input (browser automation, likely also some assistive tech paths) don't fire the `ToggleButton`'s `onClick` — only pointer clicks on the label do. Worth a `Form.Check`-based or explicit-label pattern if the panel outlives the spike.

## #65 Cross-user testimony listing on the bill page

**What landed:** `components/atproto/testimonyFanout.ts` — the pure fan-out (`collectBillTestimony` over an injectable `AtpReadClient` seam: `listRepos` walk → per-repo `describeRepo` → per-repo `listRecords` filtered by court+billId, `Promise.allSettled` so one dead repo can't empty the listing) plus `countPositions`/`filterByAuthorRole`/`slicePage` helpers and a `FanoutStats` probe logged per fan-out. `components/atproto/useAtprotoTestimonyListing.ts` — the real `AtpAgent` client, a page-lifetime single-entry promise cache (one fan-out shared by all page turns, tab clicks, and the counts fetch; browser refresh re-fans-out), and a `createTableHook` adapter returning `{ items, pagination, setFilter, counts }` — a drop-in source for an **untouched** `ViewTestimony`. `AtpBillDetails` mounts the listing in the md=8 column reserved by #64 and spreads `counts` into the bill object it hands `Summary`, so `TestimonyCounts` renders real numbers with no changes to any shared component. `components/atproto/testimonyFanout.test.ts` (13 tests, mocked client: bill filtering, sort, identity mapping, id uniquification, dead-repo tolerance, collection skip, cursor loops, page slicing, tab filtering).

**Problems discovered:**

1. **There is no cross-repo query primitive — the fan-out is O(accounts on the PDS), not O(bill participants).** Cost formula: `listRepos` pages + 1 `describeRepo` per account + `listRecords` pages per account holding the collection. Measured live: 3 seeded repos → 2+3+4 = 9 requests, 62–76 ms; 15 repos (12 curl-seeded probe accounts) → 2+15+28 = 45 requests, 167 ms. Linear in _total accounts_ — every bill page visit walks every repo on the PDS, including repos with zero testimony (`describeRepo`'s `collections` list at least lets us skip their `listRecords`). `com.atproto.sync.listReposByCollection` is typed in `@atproto/api` but **not implemented in the pinned PDS 0.4.223** — and is single-PDS anyway; multi-PDS discovery is relay/firehose→AppView or nothing.
2. **Trailing-cursor tax:** the pinned PDS returns a cursor _alongside_ the final page for both `listRepos` and `listRecords`, so every cursor loop pays one extra empty-page round trip before terminating (that's why 14 record-bearing repos cost 28 `listRecords` calls). Loops must terminate on empty-page, not absent-cursor.
3. **Pagination without an AppView is theater.** Page 1, page 2, and the header counts all require the _complete_ fan-out result; `createTableHook`'s item-derived cursor contract (`getPageKey` of the last item of a full page) is satisfied by slicing a cached in-memory array by item id. The cache is page-lifetime: refresh re-fans-out (how new testimony appears — AC), but client-side re-navigation to the same bill reuses stale data. Real freshness + real pagination = an AppView maintaining an index.
4. **The deterministic rkey collides as an app-level id across authors** — every author's testimony on a bill shares rkey `194-H1234`, breaking React keys and page cursors. Fixed by using the AT-URI as `id`, **percent-encoded** because `TestimonyItem` interpolates the id into a `/testimony/:id` href where the URI's slashes trip next/router validation ("Invalid href" dev error, observed live before encoding). The "More Details" link is dead either way (Firestore-backed page; an AT-URI is not a publishedId) — an AppView would need its own id scheme.
5. **Author-name resolution gaps:** the only name source is `describeRepo`'s `handle` (one extra request per repo); display names would need a profile lexicon or an AppView join. The org/individual distinction is unrepresentable — every author maps to `authorRole: "user"`, so ViewTestimony's Organizations tab is honestly empty (kept, as the visible artifact of the gap). `Author`'s per-row `usePublicProfile(did)` Firestore lookup misses gracefully (plain-text name, no profile link).
6. **Toolchain friction, twice:** (a) `react-async-hook`'s `UseAsyncReturn` is invariant in its deps tuple, so our `items` needs an `as unknown as` cast to satisfy `ViewTestimony`'s `UsePublishedTestimonyListing` prop type even though it only reads `items.result`; (b) jest cannot import `@atproto/api` at runtime (ESM-only dependency tree, `next/jest` doesn't transform node_modules; #59's wall again) — the fan-out lives in its own module behind the `AtpReadClient` interface specifically so tests never load the agent.
